# Acoustic Epidemiology Research System: Django Backend

Django + Django REST Framework + MySQL, with JWT login and three roles (patient, doctor, admin).

> **Honest status:** this is a **standalone scaffold**. It was written without access to your repository and
> **without Django installed or a MySQL server**, so `check`, `makemigrations`, `migrate` and `test` have **not been run**.
> Run the steps below in order. If something fails, send me the error text.

## 1. Install MySQL (Windows)

1. Download **MySQL Community Server** (MySQL Installer) from mysql.com and install it. Remember the `root` password.
2. Open **MySQL Command Line Client** (or Workbench) and run:

```sql
CREATE DATABASE acoustic_epidemiology CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'ae_user'@'localhost' IDENTIFIED BY 'choose-a-strong-password';
GRANT ALL PRIVILEGES ON acoustic_epidemiology.* TO 'ae_user'@'localhost';
GRANT ALL PRIVILEGES ON `test_acoustic_epidemiology`.* TO 'ae_user'@'localhost';  -- needed by "manage.py test"
FLUSH PRIVILEGES;
```

## 2. Set up Python (Windows, Command Prompt)

```bat
cd backend
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env
```

Edit `.env`: set `MYSQL_USER=ae_user`, `MYSQL_PASSWORD=...`, and a secret key, which you can generate with:
`python -c "from django.core.management.utils import get_random_secret_key as g; print(g())"`

## 3. Create tables and run

```bat
python manage.py check
python manage.py makemigrations accounts recordings assessments explanations
python manage.py migrate
python manage.py createsuperuser        :: creates an ADMIN (email + full name + password)
python manage.py runserver
```

**Migrations are not included**: they must be generated by your own Django version (the `makemigrations` line above).
Commit the generated `migrations/` files afterwards. If you merge into an existing project, run
`makemigrations --check` first and do not replace existing migrations.

Verify: open http://127.0.0.1:8000/api/v1/health/ (process up) and /api/v1/health/ready/ (MySQL reachable).
Run the tests: `python manage.py test`

## 4. How doctors and admins are created (never by public sign-up)

- **Admin:** `createsuperuser` (sets role=admin), or an existing admin edits a user's role.
- **Doctor:** sign in at http://127.0.0.1:8000/admin/, open **Users → Add user**, set Role = Doctor. (Or promote a registered user.)
- **Doctor → patient access:** under **Doctor patient assignments**, link a doctor to their patients.

## Access policy (default, please confirm it matches your project)

| Role | Recordings | Assessments | Explanations |
|------|-----------|-------------|--------------|
| Patient | upload; see own only | see own; cannot edit | see those on own assessments |
| Doctor | view assigned patients only | view assigned; add review notes | view assigned; create |
| Admin | view all | view all; add review notes | view all; create |

Other people's records return **404** (not 403), so their existence isn't leaked.

## API reference (base `/api/v1/`)

| Method & path | Who | Notes |
|---|---|---|
| `GET health/` | anyone | `{"status":"ok"}` |
| `GET health/ready/` | anyone | tests MySQL; `503` if down; also reports `ml_model` |
| `POST auth/register/` | anyone | patient only; any `role` sent is ignored |
| `POST auth/login/` | anyone | `{email, password}` → `{access, refresh, user}` |
| `POST auth/refresh/` | anyone | `{refresh}` → `{access, refresh}` (rotated; old one revoked) |
| `GET auth/me/` | signed in | current user; **role comes from the database** |
| `POST auth/logout/` | signed in | `{refresh}` revokes that refresh token |
| `GET recordings/` (`?status=`) | signed in | paginated, filtered by access policy |
| `POST recordings/` | patient | multipart: `audio_file`, optional `notes`, `recorded_at` |
| `GET recordings/<id>/` | permitted | metadata |
| `GET recordings/<id>/file/` | permitted | audio download (authenticated) |
| `GET assessments/` (`?status=&recording=`) | signed in | paginated |
| `GET/PATCH assessments/<id>/` | GET permitted; PATCH doctor/admin | PATCH only `doctor_notes`; sets status `reviewed` |
| `GET explanations/` (`?assessment=`) | signed in | paginated |
| `POST explanations/` | doctor/admin | `{assessment, text}` |

Auth endpoints are rate-limited (`AUTH_THROTTLE_RATE`, default `10/min` per IP). Lists use page pagination (`?page=2`, 20 per page).
Authenticated requests send `Authorization: Bearer <access>`. Access tokens last 15 min, refresh tokens 7 days.

Examples (Windows CMD: use `curl.exe`, and escape quotes or use Postman/Thunder Client):

```bash
curl -X POST http://127.0.0.1:8000/api/v1/auth/register/ -H "Content-Type: application/json" \
  -d '{"email":"asha@example.com","password":"A-strong-pass-123","full_name":"Asha","phone_number":"+91 98765 43210"}'
# 201 {"user":{"id":1,"email":"asha@example.com","full_name":"Asha","phone_number":"...","role":"patient","is_active":true,"created_at":"..."}}

curl -X POST http://127.0.0.1:8000/api/v1/auth/login/ -H "Content-Type: application/json" \
  -d '{"email":"asha@example.com","password":"A-strong-pass-123"}'
# 200 {"access":"...","refresh":"...","user":{... "role":"patient" ...}}   |   401 {"detail":"No active account found with the given credentials"}

curl http://127.0.0.1:8000/api/v1/auth/me/ -H "Authorization: Bearer <access>"

curl -X POST http://127.0.0.1:8000/api/v1/recordings/ -H "Authorization: Bearer <access>" \
  -F "audio_file=@cough.wav" -F "notes=dry cough for 3 days"
# 201 {"id":1,"status":"uploaded","assessment_id":1,"download_url":"/api/v1/recordings/1/file/",...}
```

Errors: `400` validation (field-by-field), `401` missing/invalid/expired token, `403` wrong role, `404` not found **or not yours**, `429` too many attempts, `503` database not ready.

Upload rules: `.wav .mp3 .m4a .ogg .flac`, max `MAX_AUDIO_UPLOAD_MB` (25), and the file's first bytes must match its extension.
Files are stored under `media/` with random names and are **not** served publicly; only `recordings/<id>/file/` returns them, after the access check.

## Machine learning: no model is bundled

Every upload creates an assessment with `status: "not_configured"`, empty `result_label`, and `confidence: null`.
Nothing is predicted or invented. To add a real model, set `ML_MODEL_PATH` in `.env` and implement `_predict()` in
`ml_inference/services.py`. Output is validated (label string, confidence 0 to 1) and is always labelled research-only.
Inference runs inside the upload request, which is fine for a college project but should move to a background worker for large models.

## Connect the React frontend (the one delivered earlier)

In the frontend `.env`:

```
VITE_API_BASE_URL=http://127.0.0.1:8000
VITE_DEMO_MODE=false
VITE_AUTH_MODE=token
VITE_AUTH_LOGIN_PATH=/api/v1/auth/login/
VITE_AUTH_ME_PATH=/api/v1/auth/me/
VITE_AUTH_LOGOUT_PATH=/api/v1/auth/logout/
VITE_AUTH_IDENTIFIER_FIELD=email
VITE_AUTH_TOKEN_KEY=access
VITE_AUTH_TOKEN_SCHEME=Bearer
```

Also set `CORS_ALLOWED_ORIGINS` here to your real Vite URL (check `npm run dev` output).

**Known frontend gaps (not yet verified or implemented):**
1. The frontend keeps the access token in memory only and has no refresh logic, so a **page refresh signs the user out**, and
   after 15 minutes API calls get 401. It needs to store the refresh token and call `auth/refresh/`.
2. Its logout sends **no body**, but this backend requires `{"refresh": "<token>"}`. Until fixed, logout clears the
   browser session but does not revoke the refresh token on the server.
3. `normalizeUser()` already matches this backend's `user`/`me` shape (`role`, `full_name`, `email`).
Integration should be considered **unverified** until these are fixed and tested together.
